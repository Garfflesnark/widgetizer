FIRST FIX / COMPLETED REVIEW — PROJ-049C

Problem: a ZIP with malformed pages/index.json reported success, created a partial
project and left Home unable to open. Existing page content was not parsed during
pre-import validation; unreadable collection JSON was silently skipped.

Implemented behavior:
  - Recursively parse JSON in pages/, menus/ and collections/, including language
    folders, global widgets and _order.json, plus root theme.json.
  - On a JSON syntax error, return HTTP 400 naming the archive-relative file path.
  - Run the check before creating the destination project directory or DB row.
  - Preserve the existing collection slug checks and backup-refusal cleanup flow.
  - Operational I/O errors still propagate; they are not mislabeled as bad JSON.
  - Parse UTF-8 text with JSON.parse, without stripping a leading BOM, matching
    the app's content readers. fs.readJson would accept that unreadable input.

Code locations (line numbers are those at hand-off):
  - backupContentChecks.js:60: collectionItemsProblem renamed/expanded to
    contentFilesProblem. Collection _order.json needs parsing but no item slug.
  - projectController.js:4,1456: import and call the broader helper.
    Existing call boundary at 1637 precedes ensureDir, file copy and DB creation.
  - backupImportChecks.test.js:199: nine new regression cases, including BOM input.

Regression cases cover malformed root page, translated page, global header,
translated menu, translated collection item, ordering file and theme.json, plus
successful import of the intact backup after refusal and rejection of a BOM-prefixed
page. The malformed-file cases assert the named path,
HTTP status, unchanged projects/active selection, unchanged project folders and
source media, extraction cleanup and deletion of the server's uploaded ZIP copy.
